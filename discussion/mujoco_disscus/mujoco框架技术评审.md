# MuJoCo 仿真集成方案技术评审报告

## 1. 项目背景
当前我们的机器人控制系统已基于 **ROS 2 Control** 框架完成主体开发，并通过“假硬件（Fake System）”完成了控制器（PID / 前馈 / 串级 PID / 滑模）的逻辑验证。  
下一步需要引入 **MuJoCo 物理引擎**，构建高保真的仿真环境，用于：
- 控制算法的鲁棒性测试（含接触动力学、模型摄动）
- 在不上真车的情况下进行系统集成验证
- 为未来的强化学习或 MPC 提供数据源

**核心约束**：仿真系统必须与真实机器人系统在代码层面高度复用，实现“一键切换”。

## 2. 两种候选集成方案

在调研过程中，我们发现业界目前主要有两种集成方式：

| 对比维度 | **方案一：独立桥接节点（Bridge Node）** | **方案二：原生硬件接口（SystemInterface）** |
| :--- | :--- | :--- |
| **实现方式** | 单独编写一个 ROS 2 节点，内部运行 `mj_step()` 循环，通过**话题（Topic）** 订阅命令、发布状态。 | 继承 `hardware_interface::SystemInterface` 编写硬件插件，注册到 `controller_manager`，作为标准硬件资源使用。 |
| **数据路径** | MuJoCo → Bridge(发布) → ROS 话题(序列化) → 控制器节点(订阅) | MuJoCo → Hardware Interface(内存指针) → Controller Manager(内存引用) → Controller |
| **与现有代码的复用性** | **差**。需要额外编写话题转换逻辑，现有的 `JointTrajectoryController` 无法直接驱动，需定制“中间件”。 | **优秀**。上层控制器代码**零改动**，只需在 Launch 文件中将 `hardware_plugin` 从 `fake_hardware` 改为 `mujoco_system`。 |
| **时钟管理** | 完全自由，可在独立线程中以任意频率推进物理。 | 受 `controller_manager` 的 `update_rate` 约束，需要在 `read()` 内做**时间补偿**以应对回调抖动。 |
| **生命周期支持** | 需自行处理暂停、重置、错误恢复等状态。 | 原生支持 ROS 2 生命周期（`configure` / `activate` / `deactivate`），调试方便。 |
| **通信延迟** | 较高（包含序列化、DDS 网络栈开销）。 | 极低（进程内指针引用，接近零拷贝）。 |
| **典型适用场景** | 强化学习数据采集、非标准控制算法（如自研 MPC）的快速原型。 | **标准机器人控制**（如我们的哨兵电控）、MoveIt 集成、仿真与真机无缝切换。 |

---

## 3. 关键技术风险与应对（针对方案二）

若采用方案二，评审中可能关注的核心风险是：

**风险**：`controller_manager` 的回调周期不严格固定（ROS 调度、节点负载可能导致抖动），导致物理积分步长不均匀，进而使控制器的微分项产生噪声，甚至发散。

**应对措施**：在 `read()` 中引入**基于真实时间的步长补偿机制**。

- 使用 `std::chrono::steady_clock` 测量两次 `read()` 之间的真实时间间隔 `real_dt`；
- 累加到一个 `accumulated_time_` 变量中；
- 用 `accumulated_time_ / model->opt.timestep` 计算本次应执行的物理步数 `steps_to_take`；
- 执行 `mj_step` 后，减去已补偿的时间，保留余数供下次使用。

该方案已在多个机器人仿真项目中验证，可保证**物理时间与真实时间严格同步**，从根本上避免频率耦合问题。

---

## 4. 综合评估与推荐

### 4.1 与现有软件栈的契合度
- 方案一（桥接）会破坏我们原有“假硬件 → 真硬件”的抽象层次，一旦上真车，控制器代码需要大改。
- 方案二（硬件接口）则完美延续了“假硬件”的设计理念：  
  **“假硬件”** 和 **“MuJoCo硬件”** 都实现了相同的 `StateInterface` / `CommandInterface`，上层控制器完全感知不到底层是仿真还是实车。

### 4.2 维护成本与扩展性
- 方案二的插件化架构，使得后续若要增加新的传感器（IMU、力传感器）或执行器（如机械臂），只需在 `export_state_interfaces` 中增加相应句柄，不影响上层。
- 方案一随着模型复杂度增加，话题数量会爆炸式增长，管理混乱。

### 4.3 结论
**强烈推荐采用方案二（原生 `ros2_control` 硬件接口）** 作为 MuJoCo 的集成方案。

该方案技术风险可控（时间补偿算法已有成熟实现），且能最大程度保护我们已有的算法代码资产，实现“一次开发，仿真真机共用”。

## 5. 后续实施计划

1. **硬件插件开发**：完成 `MujocoSystem` 类的实现，包含时间补偿、运动学映射（麦轮）、执行器限幅等功能。
2. **模型准备**：将哨兵机器人的 URDF 编译为 `.mjb` 二进制模型文件，优化碰撞凸包。
3. **集成测试**：
   - 在仿真环境中复现“键盘控制”与“轨迹跟踪”测试用例；
   - 对比假硬件与 MuJoCo 下的力矩输出差异；
   - 验证“跑直线偏航”等物理缺陷的排查手段。
4. **文档与培训**：输出详细的配置指南，供团队其他成员快速上手。
